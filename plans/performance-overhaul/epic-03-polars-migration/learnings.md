# Epic 03 — Polars Migration: Learnings

## Patterns Established

1. **Polars-boundary push via incremental return-type change** — ticket-008 first introduced an internal Polars implementation while keeping the `pd.DataFrame -> pd.DataFrame` public signature. ticket-009 then changed the return type to `pl.DataFrame` in one targeted step. This two-step approach (internal Polars first, signature change second) reduces the blast radius of each change and makes each diff reviewable in isolation. Established at `_resolve_temporal_resolution` in `app/services/synthesis/operation.py`.

2. **Polars internal function named with `_polars` suffix, nested inside the public method** — `_add_temporal_info_polars` is defined as a nested function inside `_resolve_temporal_resolution`, not at class level. This keeps the Polars code collocated with its fallback counterpart and avoids polluting the class namespace with implementation details. See `app/services/synthesis/operation.py` lines 462-538.

3. **Partial numpy retention inside Polars path** — `_add_temporal_info_polars` uses `np.tile` and `np.repeat` to construct `pl.Series` directly, rather than translating every numpy expression into Polars expressions. This is correct and efficient: when the result shape is known upfront and can be computed cheaply with numpy, constructing a `pl.Series` from the numpy array is idiomatic and fast. The Polars win comes from the join-based block-duration calculation (replacing a Python for-loop) and from subsequent pipeline steps, not from eliminating all numpy. See `app/services/synthesis/operation.py` lines 497-519.

4. **Join to replace Python for-loop over block lengths** — The pandas fallback used a Python for-loop over start dates to look up block durations. The Polars path replaces this with a `join` on `(START_DATE_COL, BLOCK_COL)` followed by a `with_columns` multiply. This is the canonical Polars idiom for replacing lookup loops. See `app/services/synthesis/operation.py` lines 522-535.

5. **Boundary conversion wrapper at `_resolve_bounds` call site** — Rather than changing `_resolve_bounds`'s signature, the pd/pl conversion is placed inside `_resolve_bounds` itself. `resolve_bounds` accepts and returns `pl.DataFrame`; `_resolve_bounds` converts to/from pandas around it. This keeps the inner Polars implementation clean while the outer pipeline continues in pandas. See `app/services/synthesis/operation.py` lines 2617-2645 and `app/services/deck/bounds.py` lines 1884-1916.

6. **Stub code path conversion guard** — The `_resolve_stub` path retrieves a pandas DataFrame from `CACHED_SYNTHESIS` and must convert it to `pl.DataFrame` before calling `_post_resolve`. The guard `pd_to_pl(df) if isinstance(df, pd.DataFrame) else df` handles this cleanly without breaking the common path. See `app/services/synthesis/operation.py` lines 2583-2584.

7. **`synthetize_pl` as additive method on the repository interface** — Rather than changing the `synthetize_df` signature, a new `synthetize_pl(df: pl.DataFrame, filename: str) -> bool` method is added to `AbstractExportRepository` with a default fallback implementation (`df.to_pandas()` then `synthetize_df`). `ParquetExportRepository` overrides it with a native Polars-to-Arrow path. `CSVExportRepository` and `TestExportRepository` inherit the default and require no changes. See `app/adapters/repository/export.py`.

8. **Polars-to-Arrow-to-pandas for Parquet pandas metadata** — The `synthetize_pl` implementation in `ParquetExportRepository` converts `pl.DataFrame → Arrow table → pandas → PyArrow table` before writing. This intermediate pandas conversion is necessary to generate the pandas Parquet metadata that instructs `pd.read_parquet` to restore UTC datetime dtype. Direct Polars `write_parquet` with `use_pyarrow=True` does not embed this pandas metadata. See `app/adapters/repository/export.py` lines 80-93.

## Architectural Decisions

1. **Internal bounds helpers kept as pandas** — `resolve_bounds` in `bounds.py` accepts and returns `pl.DataFrame` but converts to pandas internally for all ~10 existing helper methods (`_stored_energy_bounds`, `_stored_volume_bounds`, etc.). Rejected: rewriting all helpers to native Polars. Rationale: the helpers use complex numpy array indexing (`np.tile`, `np.repeat`, `np.zeros`) that is not trivially translatable; the conversion overhead at the `resolve_bounds` boundary is small relative to the computation; correctness risk of rewriting all helpers in a single epic was too high.

2. **`_post_resolve` entity pipeline changed to pl.DataFrame mid-pipeline** — `_post_resolve_entity` now returns `pl.DataFrame`; `_post_resolve` receives a `Dict[str, Optional[pl.DataFrame]]` and concatenates without per-entity conversion. The `pl_to_pd` conversion happens once at the end of `_post_resolve`. Rejected: keeping the concat in pandas. Rationale: eliminating the `pd_to_pl` call per entity (which was previously applied to each entity's DataFrame before `pl.concat`) removes redundant materializations proportional to the entity count (up to ~200 for UHE).

3. **`_calc_block_0_weighted_mean` migrated to Polars via group_by+agg** — The pandas implementation used `iloc[::n_blocks]` stride slicing to extract representative rows. The Polars implementation uses two `group_by` passes: one to aggregate weighted sums (producing block-0 values), one to extract representative non-grouped columns via `pl.first()`. Rejected: translating the stride-slice directly to Polars. Rationale: the group_by approach is more robust to row ordering variations and is semantically correct regardless of block ordering in the input.

4. **`_resolve_temporal_resolution` signature change in ticket-009, not ticket-008** — ticket-008 added the Polars path but preserved `pd.DataFrame -> pd.DataFrame`. ticket-009 changed the return type to `pl.DataFrame`. This phased approach meant only one file/method changed at a time and allowed the test suite to verify the internal Polars correctness before exposing the new type to callers.

5. **`pl.from_pandas` used directly in the fallback path of `_resolve_temporal_resolution`** — The fallback path calls `pl.from_pandas(_add_temporal_info(df, uow, deck_context))` rather than `pd_to_pl(...)`. The code comment explains this allows tests to patch `pd_to_pl` to trigger the fallback path without side effects on the fallback's own conversion. See `app/services/synthesis/operation.py` line 552.

## Conventions Adopted

1. **Polars path returns `pl.DataFrame`; outer public API stays pandas until forced** — Methods that form internal pipeline steps (`_resolve_temporal_resolution`, `_post_resolve_entity`) now return `pl.DataFrame`. Methods that are called by external consumers (`_post_resolve`, `_resolve_bounds`, `_resolve_synthesis`) convert back to pandas at their exit point. The conversion boundary is pushed as deep as possible without changing external contracts.

2. **Fallback path in `_add_temporal_info_polars` uses `pl.from_pandas` directly** — This enables tests to patch `pd_to_pl` (the Polars entry path) without inadvertently affecting the fallback conversion. Any future Polars function added inside `_resolve_temporal_resolution` should follow the same pattern when it contains two conversion points.

3. **`isinstance` guard before pd/pl conversion for cache-sourced DataFrames** — Any code path that may receive either a pandas or Polars DataFrame (e.g., stub paths reading from cache after ticket-009) uses `pd_to_pl(df) if isinstance(df, pd.DataFrame) else df` rather than unconditionally converting. This avoids double-conversion when the value is already a `pl.DataFrame`.

4. **Test stubs replicate closure logic** — `TestCalcBlock0WeightedMean._invoke_stub` in `tests/app/services/synthesis/test_entity_pipeline.py` reconstructs the `_calc_block_0_weighted_mean` closure logic directly rather than calling it through `_resolve_UHE_entity`. This makes the stub logic testable without needing a full UHE resolution fixture. Future closures defined inside entity resolution methods should be tested the same way.

5. **`use_pyarrow=True` and `pyarrow_options` dict for Polars Parquet write** — When writing Parquet from Polars that must be read back by `pd.read_parquet` with correct UTC datetime dtypes, the intermediate Arrow-to-pandas conversion is required to embed pandas Parquet metadata. Omitting `use_pyarrow=True` or the intermediate `to_pandas()` call on the Arrow table produces a file that reads back without timezone information. See `app/adapters/repository/export.py` lines 83-93.

## Surprises & Deviations

1. **`synthetize_pl` implementation required a pandas intermediate** — The ticket specified using Polars' `write_parquet(use_pyarrow=True, pyarrow_options={...})` to avoid the pandas-to-PyArrow conversion. The actual implementation goes `pl.DataFrame → Arrow → pandas → PyArrow table → pq.write_table`. This pandas step was unexpected and contradicts the "bypass pandas" motivation. The reason: Polars' `write_parquet` with `use_pyarrow=True` does not embed the pandas Parquet metadata (`pandas_type` annotations in the Parquet schema) that causes `pd.read_parquet` to interpret datetime columns as UTC. Without this metadata the round-trip test failed. The implemented approach produces schema-compatible output but is not strictly "pandas-free". See `app/adapters/repository/export.py` lines 83-84.

2. **`_calc_block_0_weighted_mean` Polars variant uses two group_by passes** — The ticket suggested a single `group_by` approach. The actual implementation uses two `group_by` passes: one for the weighted sum (`block_0_agg`) and one for representative non-grouped columns (`representative`), followed by a join. The single-pass approach was attempted but could not cleanly carry non-aggregated columns (START_DATE_COL, END_DATE_COL) without including them in the group keys (which would break the aggregation semantics for stacked entity types). See `app/services/synthesis/operation.py` lines 863-893.

3. **`_post_resolve` retains `pl_to_pd(valid_dfs[0])` call** — After ticket-009, `_post_resolve` receives `pl.DataFrame` objects but calls `pl_to_pd(valid_dfs[0])` to compute the column ordering for `_get_unique_column_values_in_order`. This is a pandas call inside `_post_resolve` that was not eliminated. It was left because `_get_unique_column_values_in_order` expects a pandas DataFrame and refactoring it was out of scope. The `TestPostResolveNoPdToPl` test verifies that `pd_to_pl` is not called (which it is not), but `pl_to_pd` is. See `app/services/synthesis/operation.py` line 312.

4. **`pd_to_pl_lazy` remained unused** — Epic-02 learnings flagged that `pd_to_pl_lazy` in `app/utils/dataframe.py` was exported but unused. Epic-03 did not adopt it. No lazy evaluation chain was introduced; all Polars operations remain eager. The function continues to exist as dead code.

5. **`_resolve_bounds` retains `pd.DataFrame` signature despite Polars internals** — The ticket specified changing `resolve_bounds` to accept `pl.DataFrame` (done in `bounds.py`) but `_resolve_bounds` in `operation.py` still has `pd.DataFrame` in its signature. The conversion happens inside `_resolve_bounds`. This means there is one extra `pd_to_pl` call at the bounds boundary that could be eliminated if `_post_resolve` were changed to return `pl.DataFrame`. That change was intentionally deferred; the current design keeps the downstream consumer interface stable.

## Recommendations for Future Epics

- **`_post_resolve` currently converts to pandas at exit; making it return `pl.DataFrame` would eliminate the last pd/pl round-trip in the main pipeline** — The chain `_post_resolve → _resolve_bounds → _export_scenario_synthesis` would then operate fully in Polars. The only blocker is that `early_hooks` and `late_hooks` inside `_post_resolve` receive a `pd.DataFrame`. Migrating those hooks is the prerequisite. See `app/services/synthesis/operation.py` lines 297-321.

- **`synthetize_pl` could be made truly pandas-free by building Parquet metadata without a pandas round-trip** — The current implementation embeds pandas metadata via an Arrow-to-pandas conversion. An alternative is to construct the Arrow schema with explicit UTC timezone annotations before calling `pq.write_table`. This would eliminate the last pandas conversion in the export path. Evaluate with a benchmark before committing to it.

- **`_calc_block_0_weighted_mean` now runs two group_by passes** — Profile this against the pandas fallback for a large UHE case (200 scenarios × 60 stages × 3 blocks × many UHEs). If the two-pass group_by is slower than the pandas stride-slice approach for small DataFrames, consider a lazy evaluation alternative or restoring the pandas path for small entity counts.

- **`pd_to_pl_lazy` in `app/utils/dataframe.py` is still dead code** — Either adopt it in a lazy evaluation chain (suitable for the stats export where a large concat is followed immediately by deduplication) or remove it before the module is widened further.

- **Unit tests for `_calc_block_0_weighted_mean` use reconstructed closure logic** — This creates a maintenance burden: if the closure changes, the test's reconstruction must change too. Consider extracting the closure as a `@staticmethod` on `OperationSynthetizer` so it can be imported and tested directly without reconstruction. This applies to all closures introduced in the entity resolution methods.
